# 备份恢复手册（D7-3 · 运维与应急包之三）

---

## 1. 备份策略与口径

| 项 | 口径 |
|---|---|
| 备份对象 | server/data 目录全量（JSON 文件存储的全部业务数据：projects / users / accounts / topics / drafts / moments / sessions / materials / course / pools / audit / ledger / scan_log / signals / costs） |
| 频率 | 每日全量一次，固定 23:30（当日写操作全部完成后） |
| 方式 | 打 tar 包 + 异地留存 |
| 保留 | 本地保留 ≥30 天；异地副本（网盘 / 另一台机器 / 移动硬盘）保留 ≥30 天 |
| 命名 | `data-YYYYMMDD.tar.gz`；发布前备份命名 `data-pre-release-YYYYMMDD-HHmm.tar.gz` |
| RPO | ≤24 小时（每日全量，最坏丢失当天 23:30 之后至故障点的写入） |
| RTO | ≤4 小时（从发现故障到服务恢复可用，含备份传输与复验） |

说明：本系统为 JSON 快照按日保留，时间点恢复（PITR）的粒度为「天」——恢复到某日备份即恢复到该日 23:30 的状态；同一天内的中间状态不做重放。此口径已在验收时与客户确认。

## 2. 每日备份操作

```powershell
# 在项目根目录执行（可加入计划任务 schtasks 每日 23:30 自动跑）
$stamp = Get-Date -Format "yyyyMMdd"
tar -czf "backups\data-$stamp.tar.gz" -C server data
# 异地留存：将当天 tar 复制到异地位置
Copy-Item "backups\data-$stamp.tar.gz" "<异地路径>\data-$stamp.tar.gz"
# 核验三步：存在 / 大小 > 0 / 抽样可解析
dir backups\data-$stamp.tar.gz
tar -xOf backups\data-$stamp.tar.gz data/projects.json | ConvertFrom-Json | Out-Null
echo "backup ok $stamp"
```

核验失败处置：按《告警处置单》卡片 5（备份任务失败）执行，当日手动补做全量备份。

## 3. 恢复演练剧本（三则，每季度轮换一则）

### 剧本一 · 全量恢复（模拟磁盘损坏后整体重建）

| 步骤 | 操作 | 验证 |
|---|---|---|
| 1. 准备 | 在演练机（或本机停服演练）准备干净目录，确认有 ≥30 天内最近一份 tar | tar 存在且核验通过 |
| 2. 恢复 | `mkdir server` 后 `tar -xzf backups\data-YYYYMMDD.tar.gz -C server` | server/data/*.json 齐全（15 个集合文件） |
| 3. 启动 | `cd server && node server.js` | 控制台正常，/api/health `ok:true` |
| 4. 复验 | 登录 admin → GET /api/topics?projectId=p-zeyu → GET /api/sessions → 打开门户首页 | 数据与备份时点一致：选题池 6 条、在跑场次含「有流量, 却卡在变现」等 |
| 5. 计时 | 记录从开始到复验通过的耗时 | ≤4 小时（RTO 口径），实测一般 <15 分钟 |

### 剧本二 · PITR 模拟误删场次回滚（JSON 快照按日保留实现时间点恢复）

场景：周三上午误删了某个场次（如直接改写 server/data/sessions.json 导致场次丢失），需要回到周三之前的状态。

| 步骤 | 操作 | 验证 |
|---|---|---|
| 1. 确认损坏 | 停服（Ctrl+C）；打开 server/data/sessions.json 确认场次缺失 | 记录缺失场次 id 与标题 |
| 2. 取昨日备份 | 解压到临时目录：`tar -xzf backups\data-<昨日>.tar.gz -C restore-tmp` | restore-tmp/data/sessions.json 中该场次存在 |
| 3. 时间点恢复 | 用 restore-tmp/data/sessions.json 覆盖 server/data/sessions.json（如当日其他集合也有误写，则整套用昨日备份覆盖，接受回到昨日 23:30 的口径） | 覆盖后 json 可解析 |
| 4. 重启复验 | 启动服务，查场次列表与物料/正课进度 | 误删场次恢复；进度为昨日 23:30 时点状态 |
| 5. 口径说明 | 当日 00:00 至恢复点之间的新写入不重放，需人工补记（如当天上午已标已发的物料，按已发历史补标） | 补记完成并在演练记录中注明 |

### 剧本三 · 单文件误删找回

场景：单个集合文件（如 course.json，正课数据）被误删，其余数据完好。

| 步骤 | 操作 | 验证 |
|---|---|---|
| 1. 定位 | 停服；确认 server/data/ 下缺失文件名 | 仅该文件缺失 |
| 2. 抽取单文件 | `tar -xOf backups\data-<最近>.tar.gz data/course.json > server\data\course.json` | 文件生成且可解析 |
| 3. 一致性检查 | 核对该文件中的 sessionId 均存在于 sessions.json | 无孤儿记录 |
| 4. 重启复验 | 启动服务，查任一场次正课表 | 正课 5 天列表完整，已发状态与备份时点一致 |

## 4. 演练节奏与记录表

- 节奏：每季度 1 次，三则剧本按 剧本一 → 剧本二 → 剧本三 → 剧本一 轮换；服务期（3 个月）内至少完成一轮。
- 参与人：交付方运维 + 客户方管理员各 1 人（交接后由客户方管理员独立执行，交付方旁观）。
- 判定：RTO ≤4 小时、数据与备份时点一致、复验全部通过，记「通过」；否则记问题、整改后两周内重演。
