# 告警处置单（D7-4 · 运维与应急包之四）

使用口径：每张卡片独立成卡，触发即按卡执行。第一响应指从发现（或接到报障）到完成初步定位并给出处置动作的时间。缺陷分级：P0 15 分钟响应、24 小时修复；P1 1 小时响应、3 个工作日修复；P2 下迭代（≤5 项）；P3 排期。

---

## 卡片 1 · 服务不可达（P0）

| 项 | 内容 |
|---|---|
| 触发条件 | http://127.0.0.1:8399/ 打不开，或任意接口连接超时 / 拒绝连接 |
| 第一响应（15 分钟内） | ① 确认范围：仅本人还是全员；② `tasklist /fi "imagename eq node.exe"` 查进程；③ 进程不在则直接重启 `cd server && node server.js`，在则查端口占用 `netstat -ano /findstr 8399` |
| 排查步骤 | 1. 进程在但端口被占：杀掉占端口的旧进程再启动；2. 进程反复退出：看控制台报错，常见为 data 目录权限或磁盘满；3. 启动正常但外部访问不通：检查 HOST 是否仍为 127.0.0.1、防火墙；4. 以上排除仍不通 → 按回滚流程恢复上一可用版本 |
| 升级路径 | 15 分钟内未恢复 → 通知双方接口人，按 P0 立缺陷，24 小时修复承诺计时开始 |
| 恢复确认 | /api/health 返回 ok:true；登录 + 列表 + 任务状态三项冒烟通过；连续观察 30 分钟无复发 |

## 卡片 2 · 健康检查失败（P0/P1 按影响定级）

| 项 | 内容 |
|---|---|
| 触发条件 | `curl http://127.0.0.1:8399/api/health` 非 200，或返回体 `ok` 不为 true，或 version 与部署版本不一致 |
| 第一响应（15 分钟内） | ① 重试 3 次排除瞬时抖动；② 记录返回体（status code + body）与最近一次发布时间；③ 对照发布记录判断是否新版本引入 |
| 排查步骤 | 1. 404/405：路径或方法打错，核对 /api/health；2. 500：看控制台 `[cpl-server] error:` 堆栈，多为 data 目录损坏 → 停服，按《备份恢复手册》剧本一恢复最近备份；3. version 不一致：有旧进程残留，按端口占用处理后重启；4. 刚发布后失败 → 直接走《发布与回滚-runbook》回滚 |
| 升级路径 | 依赖 data 损坏或 500 类错误 → P0；仅 version 展示类问题 → P1 |
| 恢复确认 | 健康检查连续 5 分钟正常（每分钟 1 次）；dataDir 指向正确目录；uptimeSec 归零（确认重启生效） |

## 卡片 3 · 生成任务失败率升高（P1）

| 项 | 内容 |
|---|---|
| 触发条件 | 出稿 / 朋友圈生成 / 正课正文生成类接口失败（503 或超时）明显增多；或前端普遍反馈「生成中…」超过 2 分钟 |
| 第一响应（15 分钟内） | ① 用 `LLM_PROVIDER=fail` 排除法确认是否主备同时异常（生产不设此变量）；② `curl /api/cost-report` 看 failovers 是否激增；③ 通知用户暂缓生成操作，已有草稿不丢 |
| 排查步骤 | 1. failovers 激增且全部失败：主备供应商均不可用（503 LLM_ALL_PROVIDERS_FAILED）→ 等供应商恢复，期间只读功能不受影响；2. 偶发失败：网络抖动，前端重试即可；3. 特定 prompt 失败、其余正常：核对 server/prompts/P-0X.md.txt 是否被误改（校验文件完整）；4. 全部生成卡住但服务健康：看进程 CPU，必要时错峰重启 |
| 升级路径 | 持续 1 小时未恢复 → P1 立缺陷；影响当天公开课正课发布 → 升级通知双方接口人协调人工发稿预案（复制前一日已生成物料） |
| 恢复确认 | 连续 10 次生成类调用成功；/api/cost-report 的 failovers 不再增长；通知用户恢复使用 |

## 卡片 4 · 磁盘占用 > 80%（P1）

| 项 | 内容 |
|---|---|
| 触发条件 | 数据盘使用率超过 80% |
| 第一响应（15 分钟内） | ① 确认占用大头：`Get-ChildItem -Recurse | Sort-Object Length -Descending | Select-Object -First 20`；② 常见嫌疑：backups 目录堆积、日志重定向文件膨胀、data-broken 临时目录 |
| 排查步骤 | 1. backups 超 30 天的 tar 直接清理（保留策略见《备份恢复手册》）；2. 异地留存确认后再删本地旧备份；3. 日志轮转（按周切割，保留 4 周）；4. 都不是 → data 目录异常膨胀，检查是否有集合文件写入风暴（audit / ledger 增长异常），按卡片 2 的 500 排查 |
| 升级路径 | 清理后仍 > 80% → 扩容或迁移数据盘（P1）；磁盘写满导致服务写失败 → 先恢复空间再按卡片 2 处置 |
| 恢复确认 | 使用率回到 < 70%；服务写操作正常（做一次「标已发」类的轻量写操作验证落盘） |

## 卡片 5 · 备份任务失败（P1）

| 项 | 内容 |
|---|---|
| 触发条件 | 当日 23:30 备份未生成，或 tar 文件大小为 0，或抽样 json 解析失败 |
| 第一响应（15 分钟内） | ① 手动重跑备份命令（见《备份恢复手册》第 2 节）；② 检查磁盘空间与 backups 目录权限 |
| 排查步骤 | 1. 磁盘满 → 先按卡片 4 处理再重跑；2. 计划任务未触发 → schtasks 检查任务状态与执行账户；3. tar 生成但解析失败 → 怀疑写盘进行中被打包，改为停服窗口（23:25 停、23:30 备份、23:35 起）执行；4. 连续两天失败 → 立缺陷 P1 |
| 升级路径 | 连续两天失败或异地留存缺失 → 通知双方接口人；期间禁止一切发布（发布前备份是硬前置） |
| 恢复确认 | 当日补备成功且三步核验通过；连续 3 天备份正常后才解除观察 |

## 卡片 6 · 合规拦截率回退 > 2pp（P1，业务质量类）

| 项 | 内容 |
|---|---|
| 触发条件 | 周度统计的合规第一层拦截率（命中风险词的稿子占比）较上周下降超过 2 个百分点（该拦的没拦住） |
| 第一响应（15 分钟内） | ① 跑 `node test/_calib.js` 看合规命中是否仍全 OK；② 抽 10 篇当周已发稿人工复查 |
| 排查步骤 | 1. 校准脚本报异常 → 规则库被改动，回退 config.js；2. 脚本正常但人工抽查发现问题 → 疑似绕行写法（全角 / emoji 插入等变体），收集样例补充规则库（属缺陷修复）；3. 生成源头变化（新对标赛道用语不同）→ 补充该赛道专项词表；4. 同时检查第二层语义词表是否同步 |
| 升级路径 | 确认存在漏拦 → P1 立缺陷（漏检率口径 ≤1%，超出即违约线），3 个工作日内修复并补评测用例 |
| 恢复确认 | 新用例入 D5 评测集并全绿；随后一周拦截率回到基线区间；人工抽检 10 篇无漏拦 |

## 卡片 7 · 像你度周均回退 > 5pp（P1，业务质量类）

| 项 | 内容 |
|---|---|
| 触发条件 | 像你度周均值较上周下降超过 5 个百分点（基线口径：出稿线 ≥90，周均 ≥93） |
| 第一响应（15 分钟内） | ① 跑 `node test/_calib.js`，看种子文案与生成稿像你度是否仍全部 ≥90；② 拉当周「换一换」次数对比（/api/audit 过滤 swap 类动作） |
| 排查步骤 | 1. 校准出现 LOW → 生成引擎或声纹样本被改动，回退；2. 校准正常但线上偏低 → 多为当周口吻样本输入减少（五源中声纹引擎 / 案例库未更新），补料；3. 换一换次数激增 → 用户对当前方向不买账，安排双周运营卡点辅导对齐偏好；4. 个别账号持续低 → 该项目声纹样本不足，安排补采 |
| 升级路径 | 连续两周回退 → P1 立缺陷并触发一次专项校准；同时暂停该项目的自动出稿，改人工复核后放行 |
| 恢复确认 | 校准全 OK；随后一周像你度周均回到 ≥93；出稿线 90 的自动重写机制工作正常（观察是否有自动重生记录） |
